# Spec 004 — Web app (`apps/web`)

Status: implemented (`apps/web`); session length, the start flow and Home for a new player changed in Spec 005; focus mode (the lantern scene, frost mask, Ready/Set/Go countdown, the glow after a press, and the game variant's points) in Spec 006; Home's hero and lantern week, the personal best and the skies gallery in Spec 007
Design note: `docs/design-note.md` §3, §6, §7

## Goal

A React app where a player plays the focus check, sees what happened in that session, and sees how they are doing over time. It talks only to the API (Spec 003): it never computes or sends a score.

## Players on this device [P]

- On first visit the app creates an anonymous player (`POST /api/players`) and keeps the token in `localStorage`.
- **Local profiles.** A device can hold several players, each with a name the player types (e.g. "Alex"). The name is stored **only in this browser** and never sent to the server, which still knows nothing but a token hash. The header shows the active player as an avatar (their initial); its menu lists the players here to switch between, then **Manage players**. The menu follows the WAI-ARIA menu-button pattern (keyboard open, arrow keys, Escape closes and returns focus). App-wide notices (a player deleted, or removed because the server no longer knows it) appear as a dismissible bar under the header; when several players are removed at once, one notice gives the count ("2 players no longer exist on the server and were removed from this device."). This is how several people share one device, and how the demo shows that each player sees only their own data: the server returns a player's sessions only for that player's token.
- **Manage players** page (`/players`, title "Players"), like the profiles screen of a shared streaming account: whoever holds the device holds every player's key, so the page manages every player here rather than pretending only the active one can be changed. One short paragraph explains that each player's sessions are stored on the server under their own key while this browser holds the keys and the names, so clearing its data loses access to every player's history (there is no recovery, by design). Then a list with one row per player: the name, "Playing now" on the active one, and **Rename** and **Delete** on every row. Switching stays in the avatar menu. One row is open at a time. Rename turns the row into a name field with Save and Cancel (Escape cancels); Save is disabled until the name differs from the current one (ignoring surrounding spaces, never blank); focus then returns to Rename. Delete opens a confirmation under the row ("This cannot be undone.", a red **Yes, delete everything for {name}** and Cancel, which gets focus and returns it to Delete). Confirming calls `DELETE /api/me` with **that player's own token**, then removes the profile here; deleting another player keeps the active one (focus moves to the title), and deleting the active one carries on as the next player (or a new one if none is left). **Add a player**, on the right of the page title, opens a modal dialog (a Name field, Create and Cancel; Escape or Cancel closes it). The new player joins the list and the page stays as it is: the active player does not change, and focus returns to Add a player.
- **Import link** `/import#token=…&name=…` (printed by `pnpm seed:demo`, to open the demo player without the browser console). The token is in the hash, so the browser never sends it to a server or a request log; the page removes the hash from the address bar at once (`history.replaceState`). It checks the token with the API (`GET /api/sessions`), then adds the player here and makes it active, or switches to it if this device already has that token (no duplicate), and opens Progress. An unknown token, a link without a token, or an unreachable server each get a plain explanation and a link back home, and nothing is added.
- If the API answers `401` for a stored token (the player was deleted elsewhere), the app removes that profile and says so.
- Switching or deleting a player remounts every screen, so no screen can show the previous player's data or keep an open confirmation (which would then act on the next player).

## Flow

```
First session:  Home ──▶ Step 1: How it works ──▶ Practice ──▶ Step 2: Before you start ──▶ Countdown ──▶ Trials + probes ──▶ Submitting ──▶ Results
                                              ▲                    │ Practice again
                                              └────────────────────┘
Returning:      Home ──▶ Before you start ─(Start / Skip and start)──▶ Countdown ──▶ Trials + probes ──▶ …
                           └─ How to play ──▶ Step 1 (Try a short practice, or Skip practice ──▶ Step 2)
During countdown, trials and probes (focus mode): leave the tab ──▶ "Session voided" (Play again ──▶ Before you start, or Back to home)
During countdown, trials and probes (focus mode): Stop (×) or Escape ──▶ "Session stopped" (Spec 009; same two ways on)
Home ──▶ Progress; avatar menu ──▶ Manage players, Appearance (Spec 012)
Any unknown address ──▶ "Page not found"
```

A player is **returning** once they have a completed session (`GET /api/sessions` is not empty); otherwise it is their first session.

**Session 1 in words [P].** Spec 002 leaves the first completed session out of the starting point (`practiceSessions`). The player has just done the practice round before it, so the app never calls this full check "practice": it is "your first check", for getting used to the pace, and "not counted" toward the starting point, which is built from checks 2–6. The word "practice" is kept for the 12-trial practice round only.

**Step bar (Spec 005).** The screens before a session on the step-by-step path show "Step N of 2 · {name}" and a two-part bar: 1 "How it works", 2 "Before you start". Step 2 shows it only on that path (a first session, or after "How to play"); a returning player who lands on it directly sees no bar. Nothing of the kind appears from the countdown on (focus mode).

1. **Home:** "Hi, {name}" and "Two minutes. Catch every digit, hold back on 3.", which wraps naturally at any width; only "on 3." is kept together (a no-break space), so the 3 never starts a line on its own. Groups separated by thin rules, no boxes:
   - **Last 7 days:** the days played against the weekly target as a large serif number ("3 of 4 days"; from the target on: "5 days, goal reached"), then one dot per day for the last 7 local days, today last, labelled with the weekday's initial. Played days are filled sage; today has a dashed ring until it is played. The target comes from core's `PROGRESS_CONFIG`.
   - **Last check · {day}:** the latest session's "3s held back" (catch rate, `1 − commissionRate`), longest steady run and "Typical response time" (median response), named as on Results (`src/metrics/metrics.ts`), as large serif numbers with small labels, all left-aligned, the same values as Results. With no median the number is "—" with a one-line note, "Not enough data", under it. The day reads "Today", "Yesterday", a weekday within the last 7 days, then a date ("9 Nov"). With no sessions, Home shows the **What Steady does** card instead of the history blocks (Spec 005 §4)
   - Before the baseline exists: "N more sessions until your starting point".
   - A full-width **Start today's check** button.
2. **Step 1: How it works (first session, or "How to play"):** "Catch every digit. Hold back on 3.", "Digits flash one at a time. React to each one, except 3.", three cards (5 Press, 8 Press, 3 Hold back, the 3 in the warning colour), and one paragraph: "Press Space (touch: Tap the screen) as soon as you see a digit. 3s are rare, so your finger will want to press anyway. That moment is what Steady measures." A large **Try a short practice** button and, under it, "12 digits · about 30 seconds · not saved". A returning player also gets **Skip practice** (back to Before you start, answers kept).
3. **Practice (Spec 005):** 12 trials (each go digit once, two more drawn by the seed, and 2 3s, none in the first 3) that **start slow and end at the real speed [P]**: trials 1–4 show the digit for 800 ms + 1200 ms mask, trials 5–8 500 ms + 1000 ms, trials 9–12 the real 250 ms + 900 ms. The countdown comes first, as for the real session. The line at the bottom reads "Practice · Space for every digit except 3" (touch: "Practice · Tap for every digit except 3"). After each trial, feedback for 800 ms: one or two words in a pill, sage when right and in the warning colour when not (the words differ too, so colour is not the only cue): "✓ Nice" (pressed a digit), "Held back ✓" (withheld on a 3), "That was a 3" (pressed on a 3), "Missed" (no press on a digit), "Too soon" (pressed a digit under core's `anticipationMs`, 100 ms). Generated on the client and never submitted. This per-trial feedback is not a score.
4. **How the practice went (Spec 005):** no longer a screen of its own. At the top of step 2, one line ("Practice: 2 of 2 3s held back · 9 of 10 digits caught", plus "· N too early" when any), the tip below and a **Practice again** link. The tip rules, unchanged from the earlier practice-result screen: "Nice warm-up", "Here is how the practice went. Nothing was saved.", then three serif numbers: **3s held back** (x / 2), **digits caught** (x / 16; a press under 100 ms is not a catch) and **too early** (presses under 100 ms on a digit). Then **one tip**, about the most common slip (ties: pressed on a 3, then missed, then too early):
   - pressed on a 3: "You pressed on one 3 / every 3 / some 3s. That is normal: in the real check they are rare and come at full speed.";
   - missed: "N digits passed without a press. Press for every digit except 3: a press still counts after the digit turns into ⊗.";
   - too early: "N presses came before the digit could really be seen. Wait for each digit, then press.";
   - none: "No slips. The real check runs at full speed the whole way, so a few slips there are normal."
     These counts are computed in the browser from the practice's own presses, only for this screen; they are never sent or stored, and they are not a score. **Practice again** replays the practice and returns to step 2 with the answers kept.
5. **Step 2: Before you start (check-in, optional), shared by new and returning players:** "How are you today?", "Optional. It helps you spot patterns later; it never changes your score.", then **Sleep** (Poor / OK / Good) and **Stress** (Low / Medium / High) as chips, none chosen by default. Answers are sent with `POST /api/sessions`; a group left empty is left out. Then three points as a ruled list, each with a small round icon: "About two minutes, at full speed", "A few times we ask where your mind was", and, in the warning colour, "Stay on this page: leaving cancels the session". A large **Start** button, then **Skip and start** (bottom left: start without any check-in, even if a chip was chosen; the chips are cleared; named so since Spec 010) and **How to play** (bottom right: step 1; the answers are kept). Start and Skip and start begin the countdown.
   - **Countdown:** 3 s before the first trial. It must never look like a stimulus, and it shows **no number**: counting "3, 2, 1" would put a 3, the digit to hold back on, on screen just before the trials. A thin ring fills over the 3 s (with reduced motion it does not sweep but fills a third at a time, once a second), with "Finger on Space" (touch: "Finger on the screen") under it; the bottom line reads "Starting…". The digit area stays empty. Only the display changed: the countdown's length and the trial clock are as before.
6. **Trials:** 81 trials as planned by the server (Spec 005). No score, counter, progress bar, remaining count, timer or feedback is shown during the block: knowing how far along you are changes how people respond.
   - **Focus mode** (countdown, practice or real trials, and probes): the header and all navigation are removed (the layout drops them while the block is mounted) and the stage fills the screen on the content-surface colour. The digit is Inter 700, tabular figures, near-black, centred; the five plan sizes keep the PsyToolkit ratios (48–120) of a largest size of about 240 px that scales down with the viewport. One small line at the bottom: "Space for every digit except 3" (touch: "Tap for every digit except 3"). On a touch device the whole screen is the tap area.
7. **Probes:** after each planned probe trial the clock pauses and the app asks "Where was your mind just now?" (three large buttons, On task / Drifting / Elsewhere, also keys 1–3). After the answer there is a 1-second pause, then the trials resume.
8. **Submitting:** sends `{ rts, probeAnswers }`. If the request fails, the player can retry; an identical retry is safe (Spec 003).
   - **Waiting states** (loading the player's sessions, starting the session, "Scoring your session…") are centred, with a slowly breathing ring that stands still under `prefers-reduced-motion`, and are announced as a status. Since Spec 010 this covers Results, Progress and Import as well; Home keeps the space of its panels instead.
9. **Results (Spec 004 part 3):** reached after a submit (the session comes with the navigation) or by its URL (the session is loaded from `GET /api/sessions`; one the player does not own, or an unknown id, shows the status page "Session not found", with Back to home and See your progress). It shows, all from the server's score:
   - a **one-sentence conclusion** as the first visible line (Spec 010: the title "Session complete" is for screen readers only, and the line reads "Session complete." until the history has loaded), comparing this session with a reference chosen by its place in the player's history (so it never changes later): session 1 and session 2 (only session 1 before it) get a neutral sentence that explains the starting point: "Your first full check is done. It is for getting used to the pace, so it does not count toward your starting point. Your starting point is built from your next 5 checks." and "Nothing to compare with yet: your first check was for getting used to the pace. Your starting point is built from this check and the next 4."; sessions 3–6 are compared with the median of the earlier counted sessions (at most 5; their server scores, so no score is recomputed); later sessions with the server's baseline ("where you started"). It names what was better and what was below ("Better than where you started at holding back on 3s, below at keeping an even rhythm."), or says the session was close on every measure. It only describes: it never mentions focus or attention and never judges the player;
   - each compared number shows its change with an arrow and words, so colour is only a second cue: "↑ More held back · 70% before", "↓ Fewer missed", "≈ Similar". A change within core's `PROGRESS_CONFIG.similarWithin` [P] is "Similar". Catch rate, missed digits and timing variation have a better direction (better is sage, below is red); response time is only "Faster" or "Slower", because speed trades off against errors. A footnote names the reference and adds "One session up or down is normal.";
   - the **session journey ribbon**: one cell per trial, in order, coloured by its outcome (steady, caught 3, pressed on a 3, missed digit, too early), with the longest steady run underlined and a marker after each probe trial labelled with the answer (On task / Drifting / Elsewhere). It is drawn in three labelled parts, Start, Middle and End (27 trials, about 30 s each), each with its slips in words ("2 pressed on a 3 · 1 missed", or "No slips"). Cells have a fixed width and wrap to the space, so they stay readable on a phone. The legend lists only the outcomes and answers that occur in this session; screen readers get one text summary (including each part) instead of 81 cells;
   - the session's numbers, each with only three lines: a large serif number (with its count on the same line, "71% 10 of 14"), a plain name, and the change against the reference. The research terms and a sentence about each measure are in **About these measures**, a native disclosure under the numbers, closed by default, that opens by click, tap or keyboard (no hover needed). The names and sentences come from one shared module (`src/metrics/metrics.ts`, also used by Progress): "3s held back" (catch rate, `1 − commissionRate`, with "X of Y" counted from `trialOutcomes`), "Digits missed", "Typical response time" (`medianGoRtMs`), "How much your timing varied" (`rtCv` as a percentage; rhythm variability), "Longest steady run". A `null` RT statistic reads "Not enough presses to measure";
   - **Digits missed is a count on every page** (Results, the Progress table, charts and dot plots, and every comparison: "↑ More missed · 4 before"), never a percentage: `omissionRate × 72` (every session has the same 72 digits to press for, so the count compares exactly like the rate). A median between two counts shows one decimal ("3.5");
   - any descriptive flags in plain words, framed as "about this session", never as a failure:
     - `high_omissions`: "You let many digits pass without pressing. If something interrupted you, this session may not reflect your focus.";
     - `many_anticipations`: "Many presses came very early, before a digit could really be seen.";
     - `regular_timing`: "Your timing was unusually even, which is more typical of automated input than of people.";
   - a primary "Back to home" button and a secondary "See your progress" button.
10. **Progress (part 3):** at `/progress`, linked from the header. It loads `GET /api/sessions` (one point per session) and `GET /api/progress` (everything statistical); the web app computes only the weekly target. With no sessions it says so and links to Play. Metric names, which way is better, the change words and the sentence wording come from the shared module (`src/metrics/metrics.ts`), the same as Results. Otherwise, top to bottom:
    - **Summary:** one sentence, the first visible line (Spec 010: the title "Progress" is for screen readers only). Before the baseline exists: "N more sessions until your starting point. Until then, the charts show each check." Afterwards, the recent medians compared with the baseline medians by `compareMetric` (so the "similar" band applies), in the Results wording after "Your last 5 checks: " ("Your last 5 checks: better than where you started at holding back on 3s, below at keeping an even rhythm.", or "…close to where you started on every measure, and faster."). It only describes.
    - **Last 7 days:** the same block as on Home.
    - **Recent vs. where you started:** before the baseline exists, "Your starting point is set after N more sessions" and "Your first check is for getting used to the pace and does not count; checks 2–6 set where you started." Afterwards, a row per metric: the plain name with "Higher is better" / "Lower is better" / "Neither way is better" under it, the baseline median, the recent median, and the change: an arrow and words, then "better" or "below" when the metric has a better direction ("↑ More held back · better", "≈ Similar", "↓ Faster"), coloured only as a second cue (better sage, below red). Response time is only "Faster" or "Slower". The `n` behind each median is in the cell's tooltip and in a footnote ("Where you started: the middle of sessions 2–6. Recent: the middle of your last 5 checks.", plus any median based on fewer sessions, e.g. "Typical response time, recent: 4 sessions"). On a phone the name takes its own line above the three values.
    - **Charts (Recharts):** four small line charts side by side (two columns, one on a phone), x = session number, with the plain names. Points are joined by straight lines (no smoothing, which would invent values between sessions). **With fewer than 2 sessions no chart is drawn:** each chart keeps its caption, and its plot area is a dashed box reading "Finish 1 more check to see a trend."; the legend is hidden too. The line and points are sage; the first session is a hollow circle ("First check (not counted)" in the legend, "first check, not counted" in the tooltip); a session with a flag is a hollow diamond in the warning colour, so shape (not only colour) tells them apart. The legend calls it "Has a note (listed below the charts)": under the charts, **Sessions with a note** lists each such session with its notes in words and a link to its Results, so a phone (no hover) can read them; the tooltip still shows them on hover. The list, and the legend's "Has a note", are left out when no session has a note; the baseline median is a dashed muted line once it exists. No text is drawn inside the plot: the caption above it gives the better direction ("↑ Higher is better", "↓ Lower is better", "Neither way is better"), the latest value (a serif number) and "Where you started: X" next to a dashed key. A legend above the charts names the marks. Grid and axes are faint (border and muted colours). Medians in the table are serif numbers too.
    - **Your sessions:** a list, newest first: the date and time, "Session N", a "Not counted" tag on the first session, and the session's 3s held back and typical response time. Each row links to that session's Results (`/results/:id`). Only the latest 10 are listed, with "Show all N sessions" (and "Show only the latest 10") when there are more.
    - **Exploring patterns (exploratory), collapsed by default** in a disclosure ("Exploring patterns"), so the page opens on the summary, the week, the table, the charts and the sessions. Inside, two parts:
      - **After a check-in:** a metric picker (3s held back by default) that applies to Sleep and Stress only. For each, when at least two answers have 10 sessions (`canSummarise`), a dot plot of the answers that have 10 or more: each with `n`, its sessions as sage dots on a faint track, and its median as a dark bar (a different shape, not just a different colour) with the value as a serif number, so every answer shown has a median. Under the tracks, an x-axis with round ticks and labels and the metric's name and better direction. Answers with fewer than 10 are listed as "Not shown yet (fewer than 10 sessions): OK, n = 2". One sentence names the medians and ends "This is a pattern so far, not a cause.". Until two answers have 10, the part shows only "Needs at least N more sessions with a check-in." (N: what the two largest answers still lack).
      - **Before each "where was your mind?":** always the same measure, whatever the picker says, explained above the plot: how much your timing varied over the 8 digits just before each question (`preProbeWindow`), grouped by the answer, lower meaning more even. The same rules as above, counted in answers; until two answers have 10, "Needs at least N more sessions." (N: the missing answers divided by the 3 questions per session, rounded up).

## Input and timing

- **Device [P]:** a device with a coarse pointer (`matchMedia('(pointer: coarse)')`) uses **touch** (a large tap area); otherwise **keyboard** (Space). The choice is sent as `device` when the session starts, and only that input counts during the session.
- **Stimulus:** digit for 250 ms, then a mask for 900 ms (1150 ms per trial), with the digit's font size from the plan (5 sizes). This is the standard SART timing and the real session never changes it, so results stay comparable with the research and between sessions. Only practice uses slower trials (above); the runner takes an optional per-trial timing, and the window for a press is that trial's digit + mask time.
- **Clock:** `requestAnimationFrame` drives the display; the onset of a trial is the timestamp of the frame that first shows its digit. Presses use `event.timeStamp`. Both are on the `performance.now()` clock.
- **RT:** `press time − onset` for the first press in that trial's 1150 ms window, otherwise `null`. Further presses in the window are ignored, and so are key-repeat events from holding Space.
- **Which trial a press belongs to** is decided by its timestamp, not by when the event is handled: a press belongs to the trial whose window `[onset, onset + 1150)` contains it. A press after one window closes but before the next digit is on screen (at most one frame) belongs to no trial, because nothing new was visible yet.
- **The digit is drawn directly** (a DOM update inside the animation-frame callback), not through React state, so it is on screen in the same frame whose timestamp is recorded as its onset.
- **Known limits:** onset is the frame's start time, so the true display time can differ by up to one frame (about 17 ms at 60 Hz), and keyboard and touchscreen latency differ by device. Both are why results are compared only within a player, and why the device is stored.
- **Probes pause the clock:** the next trial's onset is scheduled only after the answer and the 1-second pause.
- **Leaving voids the session:** if the page becomes hidden during the countdown, trials or probes, the session is abandoned: nothing is submitted, and the player sees the status page "Session voided" ("You left the page while it was running. Leaving the page interrupts the timing, so this session was not saved."), with **Play again** (to Before you start) and **Back to home** (design note §5). During practice the page reads "Practice stopped"; Play again goes back to step 1 for a first-time player, otherwise to Before you start.

## Status pages

One shared component (`src/ui/StatusPage`) for every "this did not work" page: a small round mark (`!` in the warning colours for a voided session or practice, `?` otherwise), a serif title, the reason in a sentence or two, a large primary button and an optional secondary link. Used for: Session voided / Practice stopped (Play again, Back to home), Session not found (Back to home, See your progress), and **Page not found**, the catch-all route for any unknown address, inside the normal layout with the header (Back to home, See your progress). Since Spec 010 also every screen that cannot load (Try again, Back to home) and a failed import link, with the error in plain words.

## Accessibility and look

- "Quiet paper" look (approved design, 2026-11-16): warm paper surfaces, a sage accent, Fraunces headings and Inter text. Every colour, font, size, space and radius is a CSS variable in `src/styles/tokens.css`, with a dark set for `prefers-color-scheme: dark`; text colours are adjusted where needed to meet WCAG AA. Shared controls live in `src/ui` (Button, Chip/ChipGroup on native radios, Card) with CSS Modules.
- Calm, high-contrast colours; respects `prefers-reduced-motion` (no animated transitions) and the system colour scheme, unless Light or Dark is chosen in the avatar menu (Spec 012).
- Everything outside the trial block works with a keyboard and a screen reader. During the block, the digit area is not announced (it would interfere with the task).
- Usable at phone width.

## Test cases

**Unit (Vitest, jsdom)**

- Trial runner, driven by synthetic frame and press times:
  - RT = press − onset of the frame that showed the digit;
  - only the first press in a window counts; key repeats are ignored;
  - a press after 1150 ms belongs to the next trial once its digit is shown, and to no trial in the gap before that;
  - a press handled after a later frame still counts for the trial whose window contains its timestamp;
  - no press → `null`;
  - the clock pauses at a probe and resumes after the answer plus 1 s;
  - a full session driven by synthetic frames has one RT per trial and one answer per probe, passes core's `validateSubmission`, and takes at least `SUBMIT_CONFIG.minElapsedMs`;
  - practice mode shows the right feedback after each trial.
  - a trial with its own timing shows the digit and mask for that long, and its press window is that long.
- Practice plan: trials 1–6, 7–12 and 13–18 use the three practice speeds; the last six use the real timing.
- Play screen, driven by a fake frame clock: a first-time player goes step 1 → practice → step 2 → countdown, with "Step N of 2" on those screens and never during the block; the practice hint stays visible; the practice line counts 3s held back, digits caught and presses too early, nothing is sent to the server, and the tip names the most common slip; each of the five feedback pills appears; Practice again replays it. A full session's submitted body passes `validateSubmission`; hiding the page mid-session shows "Session voided", submits nothing, and Play again starts a new session; leaving the practice shows "Practice stopped" and Play again returns a first-time player to step 1.
- Practice result (pure functions): the counts from hand-made trials and presses (a press at 99 ms is too early, at 100 ms it is caught); the tip for each slip, its tie order, and "no slips". The runner's practice feedback calls a press under 100 ms on a digit "too soon" and any press on a 3 a press on a 3.
- Before you start and flow: a returning player lands on Before you start (Sleep and Stress chips, none chosen; the three points; Start, Skip, How to play) with no step bar; Start goes straight to the countdown with the chosen answers; Skip sends no check-in even if a chip was chosen, and clears the chips; How to play shows step 1, and Skip practice returns with the answers kept; practising from there leads back to step 2 with the answers kept.
- Countdown: a ring with "Finger on Space" (touch: "Finger on the screen") and "Starting…", while the digit area stays empty; at no point of the 3 s is any digit on screen, and the first trial still starts at 3 s.
- Status pages: the shared component shows title, reason, primary and secondary action; an unknown address shows "Page not found" inside the layout; "Session not found" uses the same page; "Scoring your session…" is a status while the submit is in flight.
- Focus mode: while the block runs there is no header, navigation, progress bar or remaining count, only the one-line hint; the header returns on Results; the probe still takes keys 1–3; and React commits stay at the phase changes (countdown, probe, resume), not one per trial (checked with a `Profiler`).
- Device detection: coarse pointer → `touch`, otherwise `keyboard`.
- Metric definitions: which way is better for each metric (response time: neither), digits missed shown as a count of 72 (with one decimal only between counts), the "similar" band from config, the reference for sessions 1, 2, 3–6 and later (with and without a baseline), and every conclusion sentence, which never uses words that judge the player.
- Results screen: the conclusion for the first session (never the word "practice"), before the baseline and after it (better and below), arrows with words on each compared number, tiles with only the number (and its count on the same line), the plain name and the change, the research terms in a closed "About these measures" disclosure that opens on click, digits missed as a count compared with a count ("More missed · 4 before"), the ribbon in three labelled parts of 27 and a legend of only what occurred, one ribbon cell per trial with the server's outcome, the longest run marked, one labelled marker per probe, the tiles (including "Not enough presses to measure"), flags in plain words; it loads the session by URL when there is no navigation state, and shows "Session not found" for an id the player does not have.
- Weekly target: counts distinct local calendar days with a completed session in the last 7 days (today and the 6 days before it, by the device's clock and time zone); two sessions on one day count once; a session at 23:59 seven days ago does not count and one at 00:01 six days ago does; the per-day dots line up with the days.
- Home screen: the greeting and the start link; the shared plain names ("3s held back", "Typical response time"); with no sessions, an empty week, the first-check invitation and "6 more sessions"; before the baseline, the last check's three numbers (catch rate as `1 − commissionRate`) and the countdown; after it, no countdown, and "Not enough presses to measure" for a missing median; the weekly target from core's config and "goal reached". Week dots: weekday initials, played days and today marked. `lastCheckDay`: Today, Yesterday, weekday, then date.
- Progress screen: the empty state; the summary sentence before and after the baseline; the starting-point countdown; the baseline/recent rows with catch rate as `1 − commissionRate`, the arrow, words and better/below on each row, and `n` in the tooltip and footnote; chart captions with the better direction, latest value and where you started, and straight (linear) lines; digits missed as a count in the table and chart caption; with one session, an empty state in each chart's place and no legend, and charts from two sessions on; no "practice" on the page, the first session marked "not counted"; the sessions with a note listed under the charts with links (and no list without notes); chart points with the first (circle) and flagged (diamond) sessions told apart by shape; the session list (newest first, the first session tagged "Not counted", links to Results, the latest 10 and Show all); Exploring patterns collapsed by default; a part with fewer than two answers at 10 shows only how many more sessions it needs; otherwise only answers with a median are drawn, each with `n` and its median, an axis with ticks, the others listed as not shown yet, and the pattern sentence; the metric picker changes Sleep and Stress but not the pre-probe part.
- Profiles: create, switch, rename, remove; a `401` removes the profile; exactly one player is created on a first visit, even under StrictMode.
- Import link: a valid token adds the player, makes it active and opens Progress; the same token twice adds one player; an unknown token (`401`), a missing token and a network error each explain themselves and add nothing; the hash is cleared in every case.
- Screens: after a player switch or deletion, no open confirmation and no previous player's data are shown, even while the next player's data is still loading.
- API client: sends the bearer token; maps `400`, `401`, `409`, `422` to typed errors.

**End-to-end (Playwright, real API and database, part 3)**

- A new player goes through step 1, practice and step 2 (with the practice line), then a full session (with no header while the block runs), played by the test with real key presses (Space for every digit except 3, "1" at each probe), and sees the results page with the journey ribbon and the progress page with one session. It runs in **real time** (about 2.5 minutes): the server checks real elapsed time, and the app has no test-only shortcut.
- A second player added on the same device sees no sessions on Progress, and "Session not found" at the first player's results URL; switching back shows the first player's session again. As a returning player, Skip on the check-in goes straight to the countdown, without the rules or practice.
- Hiding the page during trials (a `visibilitychange` to `hidden`) voids the session: the page says so and offers Play again, and the API lists no completed session for that player.
- An unknown address shows "Page not found" with the header, and Back to home leads home.
- The link printed by `pnpm seed:demo` opens the demo player on Progress with the hash cleared, and opening it again adds no second copy.
- They run against the real API and Postgres (`pnpm e2e`, Chromium only) in a separate CI job, `e2e`.
