# Spec 003 — API and persistence (`apps/api`)

Status: implemented (`apps/api`)
Design note: `docs/design-note.md` §5–7

## Goal

A NestJS API over PostgreSQL that lets anonymous players start sessions, submit them for server-side scoring, and read only their own history and progress. It wraps `@steady/core` and adds identity, storage and timing checks; it does not re-implement any scoring rule.

## Identity [P]

- `POST /api/players` creates a player and returns a **256-bit random token** (base64url) once. The server stores only its **SHA-256 hash**.
- Every other `/api` route (except health) requires `Authorization: Bearer <token>`. A missing or unknown token → `401`.
- The player is always taken from the token, never from the URL or body.
- A resource that belongs to another player is reported as `404`, the same as one that does not exist, so ids cannot be probed.
- `DELETE /api/me` deletes the player and all their sessions (cascade) → `204`. The token stops working.
- A lost token means lost history. There is no recovery, by design (no email or personal data collected).

## Endpoints

| Method and path                 | Body                            | Success                                |
| ------------------------------- | ------------------------------- | -------------------------------------- |
| `POST /api/players`             | —                               | `201 { token }`                        |
| `POST /api/sessions`            | `{ checkIn?: CheckIn, device }` | `201 { id, startedAt, plan }`          |
| `POST /api/sessions/:id/submit` | `Submission`                    | `200 CompletedSession`                 |
| `GET /api/sessions`             | —                               | `200 CompletedSession[]`, oldest first |
| `GET /api/progress`             | —                               | `200 ProgressResponse`                 |
| `DELETE /api/me`                | —                               | `204`                                  |
| `GET /api/health`               | —                               | `200 { status: 'ok' }` (checks the DB) |

- `device` is `keyboard` or `touch`: the one input method the client uses for the whole session (Space, or tapping). It is required, stored with the session and returned with it, so keyboard and touch RTs are never mixed within a session.
- `plan` is `{ trials, probeAfter }`. The seed is chosen by the server (`crypto.randomInt`) and not returned.
- `CompletedSession` is `{ id, startedAt, completedAt, checkIn, device, score }`.
- `ProgressResponse` is `{ summary, checkIn: { sleep, stress }, preProbe }`, where `sleep` and `stress` map each `ProgressMetric` to a `GroupComparison` (Spec 002).
- Request bodies are validated with the Zod schemas from `@steady/core`. Unknown fields (for example a client-computed `score`) are dropped.

## Submitting a session

In order:

1. The session must exist and belong to the player → otherwise `404`. A malformed id → `400`.
2. `validateSubmission(plan, body)` (Spec 001) → `400 { message, errors }` on failure.
3. If the session is already completed:
   - an identical submission returns the stored result `200` (safe client retry), even after the session would have expired;
   - a different one → `409`.
4. **Timing plausibility [P]** (`SUBMIT_CONFIG` in core), using the server clock:
   - elapsed time since start must be at least **95% of the trial time** (81 × 1150 ms × 0.95 ≈ 88.5 s, Spec 005), else `422`. Probes only add time, so a real session is always longer.
   - a session older than **30 minutes** is expired → `422`. The client starts a new one.
5. Score with `scoreSession`, using the **stored trials** (never regenerating them from the seed), and store the raw submission, the score and `scoringVersion` in one conditional update (`WHERE completed_at IS NULL`). If a concurrent submit won the race, fall back to step 3.

Rejected submissions (steps 2 and 4) store nothing; the session stays open. A session the client abandons (for example, the player leaves the tab) is never submitted: it expires and never appears in the list or progress.

## Storage (Drizzle, PostgreSQL 17)

- `players`: `id uuid pk`, `token_hash text unique`, `created_at timestamptz`.
- `sessions`: `id uuid pk`, `player_id → players (on delete cascade)`, `seed int`, `trials jsonb`, `probe_after jsonb`, `check_in jsonb null`, `device text`, `started_at`, `completed_at null`, `submission jsonb null`, `score jsonb null`, `scoring_version int null`; index on `(player_id, completed_at)`.
- The raw submission is kept so that a future `scoringVersion` can re-score history. JSONB keeps one session in one row; trial-level SQL queries are not needed yet.
- Migrations are generated by drizzle-kit and committed (`apps/api/drizzle`).
- No IP addresses, user agents or names are stored.

## Hardening

- `helmet` headers; JSON body limit 32 kB.
- Rate limits with `@nestjs/throttler`: 120 requests/min per client by default, 10/min for `POST /api/players` [P].
- Environment validated with Zod at startup (`DATABASE_URL`, `API_PORT` default 4000, `DB_POOL_MAX` default 10, `LOG_LEVEL`, `NODE_ENV`); the app refuses to start on bad config.
- Docker Compose maps Postgres to host port 5433 so it does not clash with a local Postgres.
- Structured logs (`nestjs-pino`) with the `Authorization` header redacted.
- Graceful shutdown closes the DB pool.

## Test cases

Integration tests (Vitest + supertest) run the real app against PostgreSQL 17 in Testcontainers, with migrations applied and a controllable clock.

- **Auth:** no token, malformed header and unknown token → `401`; creating a player returns a 43-character base64url token, and only its hash is in the DB.
- **Start:** returns 81 trials and 3 probes; stores the check-in and the device; rejects an unknown check-in level, and a missing or unknown device → `400`.
- **Submit, happy path:** a perfect submission after 150 s returns the score from `scoreSession` and appears in `GET /api/sessions`.
- **Client score ignored:** a body with `score: {...}` is scored by the server, not taken as is.
- **Invalid submission** (wrong length) → `400` with errors; nothing stored.
- **Too fast** (60 s) and **expired** (31 min) → `422`; nothing stored.
- **Retry:** the same body twice → identical `200` responses, one stored result, also after the expiry time; a different body → `409`.
- **Concurrent submits:** two identical bodies at once → both `200` with the same result; two different bodies at once → one `200`, one `409`, and the stored score is the winner's.
- **Isolation:** player B gets `404` submitting player A's session; A's sessions never appear in B's list or progress.
- **Progress:** six completed sessions → a baseline exists.
- **Delete:** `DELETE /api/me` → `204`; the token then gets `401`, and the player's rows are gone.
- **Health** → `200` without a token, with helmet headers, not rate-limited.
- **Rate limit:** the 11th new player within a minute → `429`.
- **Body limit:** a JSON body over 32 kB → `413`.
- **Logs:** a request with a bearer token is logged with `authorization` redacted, and the token never appears.
- **Config:** missing or invalid environment variables stop startup with a message naming the variable.

## Amendments

- **2026-11-16:** `POST /api/sessions` requires `device` (`keyboard` or `touch`), stored in a new `device` column and returned in `CompletedSession`. Abandoned sessions are never submitted and simply expire (design note §5).

## Spec 006 additions

- `players.variant` (`plain` | `calm` | `game`): drawn at random (a third each, Spec 008; 50/50 calm/game before it) by `POST /api/players` and never changed; migration `0003` assigns existing players at random between calm and game.
- `GET /api/me` → `{ variant }` for the calling player (the practice round shows the variant before any session exists).
- `POST /api/sessions` accepts an optional `variant` (a play-test override); the session stores the variant it shows (`sessions.variant`: the override, else the player's) and returns it. `GET /api/sessions` and the submit response include `variant`.
